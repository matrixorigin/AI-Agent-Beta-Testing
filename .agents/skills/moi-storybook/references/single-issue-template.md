# MOI 业务 Storybook 单 Issue 模版

本文件包含两部分：默认使用的“业务 Storybook 模版”，以及仅在正式走查或验收时追加的“可执行验收附录”。不要把两部分无条件全部塞进 Issue。

## 使用原则

- 提报人默认只填写业务 Storybook，让客户、产品、研发和测试都能读懂。
- 测试夹具、精确步骤、断言、实际结果和证据由测试在验收附录中补充。
- 一条完整业务主线只创建一个 Issue。
- 没有真实执行时，只写目标、预期和待确认内容，不编造实际结果。
- 只有测试开始准备走查或自动化验收时，才追加验收附录。
- 不适用的章节直接删除，不保留空表格或无意义占位符。

## 推荐标题与元数据

### 标题

优先使用直白标题：

```text
[Story Book] <客户或项目> — <用户要完成的业务>
```

例如：

```text
[Story Book] 上勘院 — 工程文件信息提取流程
```

不要为了分类在标题中堆叠过多方括号、技术名词或验收状态。客户和业务场景应当一眼可见。

### GitHub 元数据

- Project：必须加入 `New MatrixOne Intelligence`。
- Labels：必须添加 `storybook`。
- Customer Label：客户需求必须添加 `customer/<客户名称>`，其中客户名称使用需求来源中确认的具体客户名称；非客户需求不添加任何 `customer/*`。
- 其他 Labels：只在来源明确且仓库中实际存在时添加。
- Assignee：默认填写 `gavin-wang-note`；用户明确指定其他 Assignee 时以用户要求为准。
- Priority / Iteration：只有来源明确时才填写，不推测。

如果因权限、字段或标签不存在而无法完成上述必填元数据，必须在交付结果中列出未完成项，不能把 Issue 视为完整交付。

## 发布前检查

### 提报时

- 标题能直接看出客户和业务场景。
- Issue 已加入 Project `New MatrixOne Intelligence`，已添加 Label `storybook`，并默认 Assign 给 `gavin-wang-note`。
- 客户需求已添加 Label `customer/<客户名称>`；非客户需求没有 `customer/*`。
- 开头能快速说明用户目标、业务流程、预期结果和当前问题。
- 需求来源类型明确；客户需求写明具体客户、来源证据和确认状态。
- 客户或项目背景有来源，推断没有伪装成事实。
- 业务目标、使用场景、业务流程和期望结果能够被非技术读者理解。
- 样例状态明确；每个 Storybook 使用符合 `#<Issue号>-<Issue名称>-样例数据` 规则的独立 S3 目录，全部原始样例已逐个原样保存并在 Issue 中写明对象位置，或明确记录阻塞；提报人无需填写专业测试信息。
- 测试新构造的样例文件使用 Issue 编号、Issue 名称、“样例数据”、序号和内容说明命名；用户原始文件没有被改名。
- 小文件即使附到 Issue 也已保存到 S3；大文件没有通过压缩、拆分或转换绕过 GitHub 限制。
- Issue 正文、评论和日志中没有 MinIO 或其他系统的账号密码、访问密钥、Cookie 或 Session。
- 已完成 Open / Closed Issue 查重；命中重复时不创建新 Issue。
- 正文没有大量空表、无意义 TODO 或无法解释的内部术语。

### 测试补充时

- 每个必须验收的场景都有真实样例数据或可复现夹具。
- 每个关键操作都有精确步骤和对应 Result ID。
- 每个 Result ID 都有可判定预期、验证方法和证据来源。
- 实际结果与预期结果分开记录。
- 缺少任一验收要素时不得标记 `READY FOR TEST`。
- 未实际执行不得标记 `PASS`。
- 所有 Scene、问题和证据都保留在同一个 Issue 中。
